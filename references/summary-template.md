# Summary Template — 要点梳理模板

Phase 3 使用。**核心要求**：每条 ≤ 3 行 / 有"在哪看"/有"做什么"。

## 1. 这个项目解决什么问题

模板：

> **业务背景**：<1-2 句，从 README / 注释 / 文档抽出>
> **目标用户**：<谁会用>
> **核心价值**：<相比替代方案好在哪 / 不做会怎样>

判断标准：删掉这段，新人完全无法回答"这项目干嘛的"。

## 2. 技术栈与决策

按"语言 / 框架 / 关键依赖 / 构建工具"四列。每条格式：

- **<技术>**：<作用> — `<在哪看>`（例：`package.json:12`）

最后一段写"为什么这么选"（从注释 / RFC / ADR / commit message 推断），推断不出来就明说"未发现显式 ADR"。

## 3. 目录结构导读

树状图（深度 ≤ 3），每个被注释的目录写 5-10 字说明：

```
src/
├── app/         # 路由与页面
├── modules/     # 业务领域（按域切分）
├── infra/       # 数据库 / 缓存 / 外部 client
└── shared/      # 通用工具与类型
```

## 4. 核心模块拆解（≤ 8 个，按重要性）

每条三行结构：

```
### <模块名>（<一句话职责>）
- 入口：<file:line>
- 依赖：<其它模块名或外部服务>
- 新人第一件事：<一个具体动作>
```

"重要性"排序规则：被其它模块引用最多 > 处理请求入口 > 配置与启动 > 工具类。

## 5. 一个请求的生命周期

挑一个最有代表性的端到端路径，写成 5-8 步的"trace"：

```
1. 用户在浏览器提交表单
2. 浏览器 → Nginx（<route>）
3. Nginx → Express app（src/app/server.ts:42）
4. Controller 校验参数（src/modules/users/create.ts:18）
6. Service 写数据库（src/infra/db/users.ts）
8. 返回响应（含缓存）
```

每步都要有可点击的源码链接。

三段：

```
### 6.1 首次拉取
git clone ... && cd ... && <install command>

### 6.2 启动开发环境
<run command>，访问 http://localhost:<port>

### 6.3 调试与热重载
<编辑器配置> / <断点技巧> / <日志位置>
```

## 7. 踩坑预警

列表，每条三段："症状 / 原因 / 规避"：

- **症状**：启动时报 `ECONNREFUSED 127.0.0.1:5432`
  **原因**：未启动 Postgres 容器
  **规避**：`docker compose up -d postgres` 或修改 `.env`

至少 3 条；深度 `deep` 时至少 8 条。

## 8. 下一步建议（按时间节奏）

```
- 入职第 1 天：跑通 §7 启动命令；读 §3 目录结构；打开架构图 HTML 浏览
- 第 3 天：读 §5 一个请求的生命周期；尝试在 dev 环境复现
- 第 7 天：阅读 §4 核心模块源码；找一个 good-first-issue
```

## 写作守则

1. **不要列文件清单而不解释** — "src/api/users.ts" 不是要点；"用户管理的入口，承接注册/登录请求"才是。
2. **每个引用都给路径** — 让新人 Ctrl+Click 能跳过去。
3. **承认不知道** — 推断不出"为什么"就写"未发现说明"，不编造。
4. **代码块最长 8 行** — 长代码改成"见 <file>:<line>"。
5. **专有名词首次出现给中英对照** — 例：依赖注入（Dependency Injection）。
6. **不重复架构图里的内容** — 架构图说明"长什么样"，导学文档说明"为什么与怎么用"。
